# Design

Planning design · KH-SL-001 · The user adopted the first-slice recommendations on 30 October 2026. Explicit implementation authorisation, execution evidence and acceptance remain pending.

## Context

See [proposal.md](proposal.md) for the outcome and exclusions. Inspection found only `src/main.rs` with the original Hello World starter, a dependency-free manifest and no main capability specifications. The domain analysis identifies semantic ownership boundaries; this design maps the first selected path to one crate without generating those modules now.

The [self-hosting plan](../../../design/self-hosting-plan.md) owns the bootstrap/authority transition. Source requirements are in ontology §§21.2–21.7. No repository material is migrated into a live Hub during this planning change.

## Goals / Non-Goals

**Goals:** choose the responsibility/dependency structure and the complete candidate → guarded publication → exact read → recovery path needed by the three capability deltas. Keep the adopted platform mechanisms behind that boundary and verify them during authorised implementation.

**Non-Goals:** fix final Rust signatures, promise arbitrary ontology predicates, stabilise a public third-party backend trait or select native database mappings. A permanently maintained parallel Markdown/graph definition is not an authority strategy.

## Decisions

### One crate with owned boundaries

Selected design: keep public contracts, model validation, application orchestration, provenance/interchange values, storage port and default file adapter as internal responsibilities of one crate. I/O-bearing public operations are asynchronous; public values identify semantic scope and revisions rather than exposing live accepted state or storage handles.

This follows the source and permits different executor/storage mechanisms without changing domain meaning. Separate crates per ontology profile would add versioning boundaries before those boundaries have demonstrated independent evolution. A database-shaped public CRUD interface would make the future backend choice part of the consumer's model.

KH-D-03 selects Rust 2024 with minimum Rust 1.85 and host-owned Tokio 1.x for the initial file adapter. The core and semantic public values remain independent of runtime resources; this does not promise that the file adapter runs on arbitrary executors. Use bounded `spawn_blocking` jobs (4 active / 32 waiting by default per backend instance, finite host-configurable limits), explicit capacity results, and caller cancellation that preserves publication ownership. Verify current-thread and multithreaded Tokio consumers, minimum Rust and current stable. The [decision register](../../../design/self-hosting-plan.md#kh-d-03--toolchain-and-executor-policy) owns the precise policy; no dependency is installed by this design.

### An explicit small bootstrap profile

Adopted profile scope is the shared identity/revision and source/document kernel plus `Requirement`, `UseCase` and the source catalogue's `satisfies` assertion. It must declare required properties, exact endpoint bindings and applicable validation rules; it cannot mean arbitrary JSON with a type label.

The profile is explicitly versioned and supplied to the new model scope. Its bootstrap definition is not generated by executing the yet-unimplemented self-model. The [seed roles](../../../design/self-hosting-plan.md#b1--retain-a-small-self-description-through-the-public-api) separate modelling vocabulary, the library being described and actual operation evidence. The adopted KH-D-01/02 [seed contract and authority map](../../../design/self-hosting-plan.md#kh-d-0102--seed-contract-and-definition-authority) define required fields, stable document fragments, source byte-range anchors and cardinalities. The profile is `knowledgehub-seed/1`; unknown normative fields/types and invalid bindings are rejected. Markdown owns narrative, graph records own identities/types/assertions, and complete seed admission includes both in one candidate. Empty scope creation is not completion of the seed.

### Validate a base-bound candidate, publish under branch guards

The application layer obtains current host authority, resolves a coherent base and prepares a typed candidate using model/provenance validation. The storage boundary receives a validated plan and its expected-head/invariant guards. Supported writers are coordinated per model branch; guards are checked at the publication boundary.

The branch head and operation receipt advance together with all required immutable content. This protects multi-record and absence-dependent invariants. Independent record saves or validation followed by an unguarded save would permit inconsistent combinations. The approach does not require a single mutable object representing every model in the Hub.

KH-D-05 selects a trusted host policy evaluator with qualified actor identity and default denial. Recheck current permissions on each new read/lookup/retry and at final write admission; that check defines the publication authorisation point. No built-in account system or mandatory seed review is introduced. A model element describing a principal or role cannot substitute for that current policy. User review of design meaning is a separate concept from runtime admission.

### Immutable file generations and recoverable operation intent

Use the source's candidate-staging, immutable snapshot and guarded reference-publication approach. A reader resolves a head once. Required snapshot content, content integrity bindings, history and the original operation receipt must be complete before a new accepted head can identify them.

Exact retries first pass current authority checks and then consult the stored operation identity/fingerprint/result before applying stale-base logic to a new write. KH-D-06 selects the operation key `(Hub, model, branch, operation ID)` bound to its actor and SHA-256 request fingerprint. `knowledgehub-request/1` uses RFC 8785 canonical JSON over the complete typed intent and verified content digests/lengths. Property ordering alone is equivalent; authored bytes and operation order remain significant. File/profile/fingerprint versions are separate. Retain committed keys and receipts for the store lifetime; no pruning or branch deletion is included. The [decision register](../../../design/self-hosting-plan.md#kh-d-0506--policy-formats-and-original-intent) owns encoding and retention details. Reopening either recovers the original committed receipt or establishes the earlier accepted state; unsupported damage is an explicit integrity failure.

KH-D-04 selects Linux x86_64/local ext4 on one filesystem, stable branch lock files with nonblocking exclusive `flock`, synced complete generations and same-directory atomic branch-reference replacement followed by directory sync. Store creation is coordinated and exclusive. Busy writers return a retryable outcome. Required artifacts and original receipts persist before head publication; a failure after replacement is uncertain. Recovery validates the referenced generation/history and never promotes an orphan. See the owning [publication protocol](../../../design/self-hosting-plan.md#kh-d-04--initial-file-support-and-publication-protocol). Process-kill evidence must not be labelled power-loss durability or support for untested hosts. No acknowledged durability promise may exceed the verified profile.

### Use the real public path for the self-description seed

After the prerequisite decisions and implementation authorisation, create a public-contract walkthrough that captures an exact source, submits the seed as an ordinary change set, inspects its receipt, closes/reopens and resolves the original content and result. The walkthrough may be an integration consumer or test; a separate command-line product is unnecessary.

Installing a prebuilt accepted snapshot by copying private files would evade the very admission and recovery behaviour the first slice must demonstrate. The full model is a later outcome, so incomplete type coverage is explicit rather than concealed by a larger import fixture.

## Risks / Trade-offs

- [The first slice contains substantial integrity work] → Keep the seed/profile and query surface small; retain the safeguards needed for the first supported write.
- [Branch serialization limits write concurrency] → Prefer a clear initial correctness boundary; later optimisation must preserve the same observable results.
- [Document and graph copies diverge] → Declare ownership by field/scope and validate required bindings within the same change set.
- [Adopted targets are mistaken for verified support] → Require explicit implementation authorisation and retain minimum-toolchain, executor, filesystem and recovery evidence before claiming support. All implementation tasks remain unchecked.
- [Self-description is mistaken for proof of correctness] → Keep requirements, actual run evidence and human assessment separate, even when they are stored in the same Hub.

## Migration Plan

No existing Hub data exists to migrate. On later authorised implementation, replace the starter target with the library, retain source files unchanged and run the first seed through public operations in an isolated test location. A failed seed must preserve the prior accepted head. Recovery of the library's operational data uses its declared protocol; reverting code is not an implicit rollback of committed model meaning.

Broader import and authority migration follow KH-SL-005/006, with an explicit baseline comparison and handover decision. The present bootstrap documents retain their authority until that recorded transition.
