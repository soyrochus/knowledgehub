# Packed derived indexes

KH-SL-013 implements `pack-derived-index-storage`. This is an adapter storage policy for disposable `hub/cache/neighbours/` and `hub/cache/text/`; accepted objects, generations, baselines, receipts and their identities retain the files/3 contract. See [files/3](files3-guide.md) and the [change](../openspec/changes/archive/2026-11-01-pack-derived-index-storage/design.md).

## Files and write protocol

Each namespace has `objects/packs/<pack-sha256>.khpack`, a matching `.idx`, `objects/catalog.json`, `views/` and `staging/`. Existing `objects/loose/` remains readable. New cache writes go directly into sealed packs, without a loose file for every node. Packs have variable encoded lengths; there is no fixed-size preallocation, mutable page table or in-place append to a published pack.

The pack grammar is the existing files/3 grammar: eight bytes `KHPACK3\n`, a big-endian u64 block count, then a big-endian u32 header length, canonical JSON block header and encoded entry stream for each block. The initial derived writer emits one block per pack. Each entry contains a u16 kind length, UTF-8 kind, 32 binary OID bytes, u64 payload length and canonical payload bytes; integers are big-endian. Entries are sorted by OID. Header `knowledgehub-pack-block/1` records codec (`raw` or dictionary-free `zstd`), logical/stored lengths, object count and SHA-256 of the decoded stream. The pack filename hashes the complete encoded file. Every object's existing kind-and-payload hash is preserved.

A normal block is at most 1 MiB decoded and 512 entries. A single larger valid object gets a dedicated block, bounded by the existing 64 MiB object limit plus framing. The writer can resolve buffered nodes before publication, and can read packs it has sealed but not yet advertised. It seals at the first applicable bound and on explicit finish. The reader verifies block checksums, object OIDs, kinds, lengths and decoder limits. Reading one entry decompresses its block, with the existing bounded decoded-block cache.

Publication reserves allocated file space, writes and syncs a unique staging file, links the closed pack to its content-addressed name, verifies the installed pack independently, and atomically installs its location sidecar. A staging hard link and final name share one allocation. Finish atomically replaces the sorted `knowledgehub-pack-catalog/1` catalog only after every new pack/sidecar is durable. The completed exact-view manifest is installed last. Incremental views use the same protocol and leave closed pack bytes unchanged. Readers coordinate with eviction through the existing adapter leases. An interrupted build can leave disposable files; it does not establish a completed view or change a durable commit receipt.

## Bounds and lookup work

Neighbour allocation remains capped at 256 MiB; text allocation remains capped at 128 MiB. Every pack, sidecar, staging allocation, catalog and view-manifest publication is reserved in 4 KiB allocation units before writing. Metadata replacement accounts both old and new files while they overlap and refunds the old file after replacement. Actual existing regular-file allocation, including interrupted debris, seeds the next writer's budget. Directory metadata is outside this regular-file quota, as in the previous backend. Existing 32-view / three-quarter-occupancy eviction rules remain. A capacity failure is explicit; packing does not silently raise a limit.

An immutable location map is shared per backend and cache namespace, with a one-million-location bound. Each new read batch checks the catalog's ordinary-file inode, length and nanosecond modification time. Healthy warm batches reuse locations rather than listing all packs or rereading every sidecar. A changed/missing catalog reloads metadata; independent backend publication and eviction are detected on the next batch. A cold read loads per-pack sidecars, reconstructing missing or invalid ones from verified blocks. Invalid requested packed data causes cache unreadiness or a verified rebuild. Accepted-data corruption remains an integrity error.

`NeighbourWork.index_bytes_read` and text `ReadWork.index_bytes_read` include cold catalog/sidecar bytes and encoded blocks read. Their `index_metadata_bytes_read` subset identifies catalog/sidecar work separately. They count reads even when served by the operating-system page cache; a warm batch avoids the whole-sidecar cost. Adapter `FileWork.neighbour_cache_peak_allocated_bytes` and `text_cache_peak_allocated_bytes` record the maximum regular-file reservation observed by that backend instance, including pre-existing allocation and overlapping publication files. They are peaks, not additional current usage or lifetime totals. No cold-preparation work is claimed as a cheap warm query.

Many tiny incremental operations can still make many small sealed packs. Quota/view eviction bounds retained cache data; general live-node collection or pack consolidation is a later optimization. Accepted-object compaction remains an explicit separate maintenance operation.
