## Goals / Non-Goals

**Goals:** remove previous canonical content, generate a fresh fully sourced files/3 self-description through public APIs, run the complete suite and record actual reopened/indexed behaviour.

**Non-Goals:** old-store conversion, preservation/import of old snapshot IDs or receipts, replay-domain continuation, backup/restore features, atomic migration exchange, automatic authority handover or fictional rent tables in the canonical model.

## Decisions

### Compatibility review after sealed derived packs

KH-SL-013 preserves files/3 logical objects, accepted revisions, public writes and the KHPACK3 decoder. It changes direct derived writes and location reuse; it is not an incompatible format revision. A rebuild remains valid and is selected to capture current implementation sources. The new run creates a new replay domain rather than migrating the old one. Existing explicit compaction packs accepted objects; neighbour/text preparation must now produce sealed variable-size packs under unchanged 256 MiB/128 MiB quotas. Validate pack filename hashes, report encoded/allocated/peak/cache counts and inspect from a second backend: cold metadata is charged once, following warm batches reuse it, and exact semantic results agree. Keep old attempt/packed-cache evidence historical and preserve unrelated orig_hub/.

### Explicit host reset with a narrow target

Add a host orchestrator, working name `scripts/rebuild_canonical_hub.py --reset`. Applying this change authorises its reset of repository-root `hub/`; no second approval checkpoint is part of the plan. The reusable command requires explicit reset intent and validates the exact repository canonical path, expected generated Hub scope, ordinary-directory status and absence of symlink/path escape before deleting anything. It refuses repository root, parent/unrelated paths and mismatched scope. If the expected canonical path is absent, it starts fresh after the same preflight.

Drain/stop all users and coordinate with existing writer locks before deletion. Remove the complete old `hub/` contents, including its generations, receipts, artifacts, caches and guide, then recreate a new files/3 store through ordinary create/register/commit operations. Do not rename the old Hub into a retained rollback copy or import its history. An optional small before-reset inventory/report outside `hub/` is evidence, not a recovery copy. Existing historical evidence under `delivery/evidence/` is outside the reset target.

This is host demonstration lifecycle management. Do not add a general destructive `OntologyHub::reset` operation or let ordinary create/open replace existing stores.

### Finish code and run the full suite before destructive reset

Complete example, capture, binding and documentation changes first. Extend verification tooling with explicit new run-specific log/manifest paths, for example `delivery/evidence/hub-rebuild/<run-id>/`; never overwrite the old full-ontology evidence.

The required successful batch is:

```text
cargo fmt --all -- --check
cargo test --offline --all-targets
cargo test --offline --doc
cargo clippy --offline --all-targets -- -D warnings
```

This includes unit, integration, internal fault/policy/replay/runtime tests and all new files/3/neighbour/query tests. Explicit public example mains are run separately because compiling all targets does not execute those walkthroughs. Record actual exit codes, output, executable/build hashes, input hashes, timestamps and observed platform. Any failed check aborts before deletion. Do not assume the earlier run's 54-test count.

Freeze the checked code/source checkpoint, capture exact inputs against that successful batch, then reset/populate. If checked input changes, invalidate the capture and rerun required checks before claiming verification. Full native checks run once for the final code checkpoint; post-population tests target the new canonical dataset and its public reads, avoiding a redundant second identical native batch unless code changed or a failure requires it.

### Fresh source capture and vocabulary bindings

Give existing loader/catalogue/inspector examples explicit `--format files3` host selection while preserving their legacy positional/default files/2 invocations. Update README commands before the checked batch. Capture the current repository, original PDF/Markdown, extraction manifests and the new run's actual verification evidence; do not reuse the older `self-model-input.json` or older passed log as current evidence.

Extend the host's explicit module/source/operation bindings for newly implemented files/3, neighbour/query APIs, orchestration scripts and run-specific evidence paths. Preserve existing semantic names where origins moved, and reject unknown origins rather than fall back to filenames. The self-description should include the newly implemented public contracts and responsible modules through its normal source-derived modelling.

Exclude `hub/`, caches, temporary outputs and prior evidence archives from recursive capture except deliberately selected historical evidence. The captured checkpoint precedes final task/evidence status updates; declare that boundary rather than claiming a live mirror or recursively rebuilding itself forever.

### Generate a new Hub, then prove its contents

Create new immutable store/replay-domain metadata. Populate the complete built-in ontology and current applicable library self-model through ordinary public operations; create new A/B explanations, native evidence bindings and original receipts for this run. Symbolic model IDs may retain their established meaning, but old store handles, snapshots and receipts are not continued or imported.

Drain/close/reopen. Run the full catalogue conformance example in an isolated fresh store, the canonical self-description and inspector, complete scrub, exact new A/B comparison/narrative/receipt/retry checks, and indexed neighbour/phrase/composite reads on actual self-model definitions. Run the rent/late-association demonstrations from KH-SL-010/011 in separate fixtures or disposable clones. They must not add invented domain concepts to the canonical library model.

A successful native batch alone does not establish successful population. Mark the rebuild complete only after all required generated-dataset checks pass. Current draft gaps, applicability and human acceptance remain distinct from structural validity.

### Explicit failure and evidence states

Keep a run status outside the deleted directory: preflight, checks-passed, reset-started, populated, verified or failed. A preflight/test failure preserves the old Hub. Once reset starts, interruption may leave no Hub or an incomplete new demonstration; report that truthfully and permit an explicit reset/retry from repository inputs. There is no promised rollback to deleted content and no silent reuse of a partial store as verified.

Publish a new completed result with scope/domain, captured sources, actual record/gap counts, new baselines/receipts, test and walkthrough outputs, storage/object/index measurements and cold/warm query work. Historical reports remain records of the removed older instance and do not prove the new one. Compare controlled unchanged-input benchmarks for format-efficiency claims; old 116 MB versus a newly expanded source model is contextual, not a byte-for-byte migration comparison.

Generate `hub/README.md` and update the current consumer guidance with the new format, explicit inspector command, source checkpoint, new evidence links and destructive rebuild instructions. These generated post-capture views are not silently new authoritative model revisions.

## Risks / Trade-offs

- [Reset destroys the old demonstration history] → this is the user's selected behaviour; retain independent older-run evidence and label the new Hub as a fresh instance.
- [Path mistake removes unrelated work] → exact canonical-path/scope validation, no symlink traversal and negative path tests before any deletion.
- [Successful tests are followed by failed population] → separate native and canonical-dataset completion statuses; retain failure output and allow explicit clean retry.
- [New modules or logs lack stable capture bindings] → update binding inventories and reject unknown origins before resetting the canonical path.
- [Rebuild appears to shrink by dropping model coverage] → verify full required source/vocabulary coverage, report actual gaps/counts and use fixed-input storage benchmarks.

## Execution sequence

First prove the orchestrator on a disposable repository-shaped fixture, including refused paths, failed checks and interrupted population. Then run the final native batch and fresh capture, explicitly delete old canonical content, populate files/3, execute reopened/scrub/indexed walkthroughs and publish the new result. The three implemented host-tooling tasks are reusable. All eight execution-dependent tasks are reset to unchecked for this new source checkpoint; the prior 7/11 snapshot is retained in delivery/evidence/hub-rebuild/resumption-20261101.md. Planning alone neither deletes data nor establishes a passing suite.
