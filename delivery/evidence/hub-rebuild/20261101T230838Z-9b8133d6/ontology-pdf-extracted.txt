A Proposal for a System Definition Ontology for the
Knowledge Hub
Draft 0.2 - 30 October 2026 - Ontology and proposed Rust library with a default file backend; adoption and
implementation remain pending.


1. Purpose and proposed outcome
This proposal defines how a Knowledge Hub could represent the knowledge needed to understand, design,
implement, operate and evolve an information system. It connects business intent, user experience, domain
meaning, functional behaviour, information structures, visual interfaces, architecture, implementation and
verification through explicit, traceable relationships.

The proposed outcome is a storage-independent System Definition Ontology: a vocabulary of identifiable
objects, their properties, the relationships between them and the rules that make a model coherent. The
ontology can be implemented in a graph database, an RDF store, a relational database or validated files
without changing its fundamental meaning.

Section 21 proposes a concrete realisation as a Rust library named knowledgehub. Its first backend uses
Markdown documents, graph JSON and versioned file artifacts. MongoDB and PostgreSQL adapters are future
options outside the first implementation; their required semantics are addressed in the API and backend
contract from the outset.

The central principle is:

    Represent concepts, behaviours, rules, representations and evidence as identifiable, versioned objects
    connected by typed relationships, with provenance attached to both objects and relationships.

A document, diagram or mockup can describe several objects. An object can appear in several documents and
views while retaining one identity. The Knowledge Hub preserves these connections so that a reader or tool
can move from a business objective to the behaviour, interface, implementation and evidence that support it.

This is a proposed synthesis of domain-driven design, experience design, requirements engineering,
behavioural modelling, provenance and delivery assurance. It is not presented as an established DDD
ontology. Established standards provide terminology and specialised representations where applicable; the
combined model and its integration rules are the proposal made here.


2. The Knowledge Hub and its boundaries
The Knowledge Hub is the central, governed repository of system-related knowledge. Its logical contents
include the system definition, original source references, interpretations, model revisions, representations,
implementation references and evidence of verification and acceptance.

A Knowledge Hub can contain one or more system models, each with an explicit scope and owner. A model
may describe a single application or a solution containing several applications, services and external-system
references. Shared concepts are connected through qualified references with clear ownership. Alternative

3. Principles
  1. Stable semantic identity. Names, filenames, positions and diagram coordinates do not identify a concept.
     Renaming or moving a representation must preserve the identity of what it represents.
  2. Explicit meaning and ownership. Types, relationships and consequential rules have clear definitions and
     owners. A familiar word can have different meanings in different contexts.
  3. One authoritative definition per scope. A field or relationship has one declared authoritative definition
      within a baseline. Narrative and structured forms must not become competing sources of truth.
  4. Versioned provenance. Definitions and assertions retain the exact source revisions, anchors,
      interpretation and review on which they depend.
  5. Complementary perspectives. Business, experience, domain, behaviour, information, visual and
      engineering models are connected views of the system. Their relationships are many-to-many.
  6. Optional channels and profiles. A background process does not need an invented screen, a pure
      calculation does not need an invented aggregate, and a system without AI does not need an AI profile.
  7. Behaviour beyond labels. Functions, transformations and interactions include contracts and
      consequential semantics, not just names and arrows.
  8. Evidence with explicit scope. Intended behaviour, implemented behaviour, verified results and human
     acceptance remain separate facts.
  9. Storage independence. Files, tables and graphs are alternative physical representations of the same
     governed logical model.
10. Progressive formalisation. The model can begin with reviewed descriptions and gain executable
      contracts and constraints where uncertainty or consequence warrants them.

5.1 Identity and revision rules
An identity survives a rename or a change of location. A revision captures a particular meaning at a particular
point in its history. Published revisions are immutable; a change creates a successor revision. If a change
introduces a genuinely different concept, it receives a new identity connected through an explicit relationship
rather than silently replacing the earlier concept.

Relationships have identities and revisions as well. A modelling statement such as "this interaction issues this
command" must remain inspectable after either endpoint changes. A baseline resolves its relationships against
exact endpoint revisions, with any explicit pinning preserved. It must not silently combine incompatible revisions
selected from different baselines.

Baseline membership is a set of explicit version bindings, not simply a timestamp or a label such as latest.
Parentage, alternatives and comparison between baselines are recorded separately.


5.2 Provenance and authority
Provenance should capture both the source and the act of interpretation. A useful reference records source
identity, immutable source revision, anchor, the statement being supported, derivation method, interpreter and
review status. Evidence may support an individual property or relationship rather than an entire document or
object.

Source status must distinguish observation, hypothesis, authored requirement, design decision, implementation
observation and validation result. Confidence supplied by an extraction tool is not approval of its interpretation.

The Hub declares whether a representation is an authoritative definition, original evidence, implementation
artifact or derived view. Existing document-owned definitions can remain authoritative while a structured model
is proposed and reviewed. If structured authoring later becomes authoritative, the migration must explicitly
replace the competing definition with a reference or derived representation.

7. Business, experience and DDD relationships
Business capability, business function and application use case answer different questions. A capability
identifies an ability the organisation needs. A business function identifies a responsibility or category of
business work. A use case describes behaviour through which an actor or system achieves an outcome.

For example, maintaining service appointments is a capability, coordinating field service is a business function,
and rescheduling a confirmed appointment is a use case. The business function can be supported through
several use cases and channels.

A journey records progression through activities and handoffs. A story expresses a need and benefit within that
progression. A requirement states a promise precisely, while a scenario supplies a concrete example and
expected result. Story maps group these elements and identify useful outcome cuts without turning the journey
into a technical task list.

DDD introduces model boundaries and consistency responsibilities. Bounded contexts own meanings and
rules; they are not automatically processes, deployable services or screens. An aggregate protects a
consistency boundary and identifies exactly one root entity. Root is a role within aggregate composition, not a
second entity created to duplicate the root's identity. Reusable value-object types and application orchestration
remain distinct from aggregate ownership.

The same word may require different types or qualified meanings. A decision can mean business decision logic,
a design choice, a review outcome or a domain entity in the described application. A function can mean
business responsibility or executable computation. Context and type identity prevent these meanings from
being merged merely because their labels match.

These DDD foundations can be mapped to the terminology in Eric Evans's DDD Reference. The broader
connections between experience, delivery and evidence are part of this proposed ontology.

A label such as Calculate appointment duration does not fully define the calculation. The model must capture
the relevant time semantics, inputs, result and errors, or point to a versioned authoritative definition that does
so.

Commands represent requests to change state. Queries represent requests for information. Use cases
establish application-level authorisation, orchestration and consistency boundaries. Domain operations
preserve domain rules. Channels such as HTTP, messages, CLI commands, schedules and UI actions bind to
these behaviours without redefining them independently.

Business decision logic can be represented through decision definitions, required inputs, rules, results and an
expression or decision-table representation. A model review decision approving that logic is a separate
governance object.


10. Event and process model
An event definition describes the meaning and contract of a fact. An occurrence records that fact in a particular
execution. A handler defines the reaction to an event. These are separate objects.

An EventDefinition should identify its business meaning, owning context, schema version, possible producer,
consumers, disclosure restrictions and compatibility policy. Its delivery contracts describe relevant ordering,
duplicate delivery, retention and recovery assumptions.

An EventOccurrence should identify the event definition/version, event identity, subject identity/version,
occurrence time, recorded time, causation, correlation and relevant producer or execution references. Sensitive
payloads may remain in an authorised native store while the Hub retains safe references and evidence.

UI events, domain facts, integration messages and operational telemetry remain distinguishable. A button
activation is not automatically a domain fact. An integration message can be derived from a domain fact
through an explicit mapping and disclosure boundary.

A process definition composes steps, guards, branches, timers, event waits, outcomes and compensations. Its
execution records the admitted steps and actual results under the versions used. Process state, aggregate
lifecycle state and UI view state retain their separate meanings even when one influences another.

Event definitions do not select an event-sourced architecture. Publication after a committed transaction,
recovery through an outbox or an external event stream are implementation mechanisms connected to the
relevant contracts. The ontology records the selected mechanism and its evidence rather than inferring it from
the presence of events.

11. Information and transformation model
The information model represents logical schemas, fields, datatypes, identifiers, units, nullability, reference
constraints and lifecycle or retention properties. A domain entity definition, an API payload schema and a
physical database table are distinct objects connected through explicit mappings.

Physical tables and columns are implementation evidence, not automatic aggregate or bounded-context
definitions. A table may implement parts of several logical structures; a domain object may have several
storage or transport representations.

change domain ownership or behaviour. A visual edge must declare whether it represents a semantic
relationship or is merely a drawing connection.


13. Architecture, security, quality and AI participation
Architecture connects logical responsibility to software components, modules, public interfaces, adapters and
external systems. Deployment definitions and instances then connect those implementations to environments,
resources and configurations. A bounded context is not automatically a deployable service, and an interface is
not automatically an HTTP endpoint.

Integration contracts describe native identity, schema, protocol, authority and error semantics. Adapters identify
the transformations that cross these boundaries. API contracts and message contracts can be imported or
generated as specialised artifacts while retaining their links to use cases and policies.

Security modelling includes principal types, roles, permissions, trust boundaries, authorisation and disclosure
policies, audit requirements, retention obligations and relevant threats. Interface visibility is not admission
authority: a hidden or disabled control cannot replace application-side enforcement. Secret material is

represented through controlled configuration references rather than copied into broadly readable model

Quality scenarios describe measurable conditions, stimulus, response and required limits. Service objectives,
capacity assumptions, observability signals, recovery procedures and deployment constraints link to those
scenarios. A measured result records the build, environment, workload and conditions under which it was
obtained.

Where AI participates, its role, tool contracts, context selection, model/prompt versions, limits and human-
review boundaries are explicit. A tool call invokes the same governed application behaviour as other channels.
Evaluation cases and actual run evidence are linked to the relevant promises. Source content, model output or
an agent role does not itself grant authority.


14. Delivery, verification and acceptance
The Knowledge Hub should connect product definition to delivery without treating planning records as proof of
working behaviour.

For this proposal, a delivery slice means a bounded increment of working behaviour that delivers one coherent,
demonstrable outcome and can be verified and reviewed as a unit. It identifies actor/trigger, observable
outcome, complete path, applicable safeguards and evidence. This is a delivery convention, not a DDD
modelling primitive.

A feature can require several slices, a slice can cross several contexts, and a slice can require several
bounded changes. Implementation tasks describe the work inside those changes. Cross-cutting deployment
verification and whole-release acceptance rehearsals can be represented as release work packages rather
than forced into the product-slice category.

Verification specifications are distinct from their executions. A test case defines an example, inputs, steps and
expected results. A test run records the exact test version, system baseline, build, environment, observed
results and evidence. A suite execution groups test runs without erasing their individual scope.

The Hub should represent the following dimensions separately:

 Dimension                               Governing records

 Definition and interpretation           Source references, interpretation records and reviews of exact model revisions.

 Implementation                          Versioned code/configuration artifacts and their declared implementation bindings.

 Verification                            Test executions, measurements, outcomes and evidence tied to the checked scope.

 Acceptance                              An authorised person's assessment of an exact scope, with conditions and limitations.


These dimensions cannot be safely collapsed into one generic status field. A reviewed requirement can remain
unimplemented; an implemented function can fail verification; a passing technical test does not automatically
establish human acceptance.

Current-state, target-design and observed-deployment baselines should also remain distinguishable. A
proposed model change records its intended delta, rationale, affected elements, evidence and review.
Accepted changes produce a new consistent baseline while preserving earlier knowledge and source bindings.

21. Proposed Rust library knowledgehub
21.1 Implementation objective and scope
Implement a Rust library named knowledgehub that provides the official application API for reading, validating,
changing, reviewing and exchanging Knowledge Hub content. The library owns the model's semantics and
guarantees; storage adapters own the mechanisms used to preserve them.

The requested name identifies a new library. A crates.io registry lookup on 30 October 2026 returned that no
crate named knowledgehub existed. Publication and registry-name availability must be checked again when a
release is prepared. This proposal does not depend on an existing package or claim that a library has already
been implemented. Registry lookup.

The first implementation includes the Rust library and one default file-based backend. It stores authored
narrative as Markdown, explicit model elements and relationships as graph JSON, and supporting content as
versioned file artifacts. It requires no database server.

MongoDB and PostgreSQL are planned alternative backends. Their drivers, configuration, deployment,
operational support, performance work and actual database parity checks are outside the first implementation.
The initial API nevertheless defines the snapshot, transaction, identity, query and portability semantics that
those adapters would have to satisfy.

An HTTP service or remote SDK could later expose the same use cases. Neither a network service nor a
particular application UI is required to establish the first library contract. Library encapsulation separates
responsibilities; enforceable isolation from untrusted callers additionally requires appropriate process,
credential and filesystem boundaries in its host deployment.

21.4 Change sets and consistency guarantees
The initial atomic commit scope is one model branch. A change set may contain several related operations,
such as revising a Markdown-owned definition, updating its structured references, adding a relationship and
recording provenance. Multi-model atomic changes are a separate capability and must not be implied by
several ordinary commits.

Every supported backend must preserve these core guarantees:

  1. A change set either commits all accepted changes and required metadata or leaves the accepted head
      unchanged.
  2. Published revisions remain immutable, and a snapshot resolves a consistent set of exact versions.
  3. The operation's expected head and relevant revision guards are checked at commit admission, not merely
      during an earlier UI or validation pass.
  4. Graph-wide constraints are protected against concurrent changes; independent record checks alone are
     insufficient where a rule spans several relationships or depends on absence.
  5. The same operation ID, scope, actor and canonical request fingerprint resolve to the original result on retry.
      Reusing that identity for different intent is rejected.
  6. No durable success acknowledgement is issued before the selected backend's commit/durability contract is
      fulfilled.




                                                                        22 / 26
system-definition-ontology-proposal.md                                                                        2026-10-30




  7. History, provenance, the new head and deduplication result are published coherently. Required change
     notifications are derived from durable committed records, not emitted as success beforehand.

The first implementation can serialise writers per model branch and use an expected-head guard. This
deliberately favours a clear correctness boundary over fine-grained write concurrency. A future implementation
can change its locking strategy while preserving the same observable outcomes.

After current access checks, an operation retry consults its deduplication record before treating the original
expected head as a new stale write. Returning an existing receipt never re-executes the mutation. A caller that
has lost access does not regain it through an old operation ID.

Validation can prepare a commit plan from a coherent base snapshot. The storage adapter applies that plan
only if its guards still hold; otherwise the caller must inspect or rebase the change and validate again. The API
must not blindly replay a stale user intention against a new head. External source acquisition and other network
work occur outside the short commit-publication boundary.

21.5 Default Markdown and graph-JSON backend
The default backend should be a portable directory with an explicit format version. One possible layout is:

This is an illustrative internal layout, not a required path convention for consumers. The snapshot manifest
binds the exact ontology/profile versions, Markdown documents, graph records, provenance, baseline
selections and content hashes needed to reconstruct that snapshot. The first implementation may use
complete snapshot generations for small models; content-addressed sharing or incremental storage can follow
without changing the public API.

Markdown documents carry readable narrative and any definitions declared to be document-owned. Stable
document/fragment identities preserve references across heading or filename changes. Graph JSON carries
explicit typed identities, relationships, revision bindings and structured definitions owned by the graph. The
authority map determines which representation owns each field; a cached structured extraction of Markdown is
marked as derived rather than becoming a competing normative copy.

An API edit to a document-owned definition must update that authoritative content and its required
graph/provenance bindings coherently. Similarly, an edit to a graph-owned relationship must not be
implemented only as a diagram or prose change. A diagram's layout remains separate presentation metadata.

Accepted snapshots are immutable. Direct editing of published snapshot files is outside the supported write
protocol. Human editing can use an exported working copy or authoring workspace whose changes are
detected, reconciled and imported through the same validation/change-set API. Imports reject malformed
metadata, unresolved required references and stale-base edits rather than silently replacing the accepted
model.

21.6 File publication and recovery
The adapter should coordinate the supported writers, construct and validate a candidate snapshot in staging,
persist its content and commit metadata, and then publish the new branch reference using the selected
filesystem's tested atomic replacement and durability procedure. Readers resolve a branch head once and
remain bound to that snapshot for the read operation.

An interrupted publication before the head advances must leave the prior snapshot usable. After a successful
head publication, the new snapshot must be complete and recoverable, including the original operation result.
Incomplete staging content is never treated as an accepted baseline; unreferenced objects may be retained for
inspection or reclaimed through a defined cleanup procedure.

Atomic rename by itself is not the complete durability or multi-file consistency contract. The implementation
must specify file and directory persistence, writer coordination, supported filesystem assumptions and recovery
after interrupted writes. A manifest must never point to missing content after an acknowledged commit within
the supported profile.

Initially support a coordinated single-host writer profile, with concurrent readers on immutable snapshots.
Multiple clients can later be served through one host service using the same writer coordination. Arbitrary multi-
host writers sharing a network folder are outside the first file-backend guarantee.

Cancellation or a lost response near commit must be recoverable through the original operation ID. The
absence of a response is not proof that the change did not commit. The caller needs an operation-status/result
lookup rather than a new identity and an uncontrolled second attempt.

21.7 Storage interface and portable query semantics
The internal storage interface should expose snapshot-bound reads and guarded commits of validated plans. It
must not require the application core to execute user callbacks inside a database-specific transaction or to
manipulate live storage objects. Each adapter owns the transaction, lock, compare-and-swap and recovery
mechanisms needed to meet the contract.

Rust traits can express this backend interface. If dynamic dispatch is selected, its asynchronous methods must
use a compatible representation, such as explicitly boxed futures; a native async fn trait method must not
simply be assumed usable through a trait object. The final internal interface should be tested before it is offered
as a stable third-party adapter API. Rust trait interfaces and dynamic compatibility.

The portable query contract must define filtering, null/missing-value distinctions, ordering, pagination,
relationship direction, traversal bounds and snapshot selection. A client should not send arbitrary SQL,
MongoDB filter documents or a vendor graph language through the official API.

The initial file backend can satisfy bounded queries through scans and rebuildable indexes. Future backends
can optimise execution while returning equivalent semantic results. Full-text ranking, vector search or other
specialised facilities can be optional capabilities, with explicit availability and result provenance; core integrity
guarantees are never optional capabilities.

Search indexes, embeddings and rendered views are derived. If updated asynchronously, their responses
identify the baseline or indexing watermark they represent. Authoritative revision resolution and commit
validation cannot silently use a stale derived index as their source of truth.

21.9 Interchange, API evolution and future service exposure
Keep the Rust API/crate version, ontology/profile version, file-format version and portable bundle version
separate. A new ontology type or adapter should not silently change the meaning of an existing API operation.
Structured errors and public contracts need an explicit compatibility policy appropriate to the crate's published
version.

Export produces a backend-neutral bundle containing selected identities/revisions, relationship assertions,
ontology/profile bindings, Markdown documents, source anchors, required artifact content or qualified external
references, baseline selections and relevant review/history records. A complete backup/export profile must also
declare how operation identities and deduplication history are retained for safe recovery and migration. A native
database dump is not the portable interchange contract.

Import stages and validates its scope before promotion. Moving the same model from files to a future database
backend should preserve meaning, identity, exact revisions, history and original source hashes; it need not
preserve physical row order, native storage IDs or database JSON formatting. Semantic content hashing needs
a declared canonical encoding, while original-source hashing refers to the retained original bytes.

A later HTTP service should call this library rather than reimplement its validation and commit rules. Its
authentication, transport errors and remote-client behaviour are an additional adapter boundary. An embedded
library API is the first deliverable; HTTP service implementation, remote SDK, FFI and crate publication are
outside this first implementation scope.
